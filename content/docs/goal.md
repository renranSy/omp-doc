# 目标模式

目标模式 将单一目标转变为自动驾驶会话。设定一次目标 `/goal <objective>`，并且在每个回合后，omp 都会注入一个隐藏的延续转向，重新提交相同的目标。当模型调用时循环停止 `goal` 工具与 `op: "complete"` 并在Token预算用完或暂停或放弃时证明每个可交付成果。

当下一步很明显但工作总量并不明显时（长时间迁移、扇出清理、“继续进行直到测试套件变绿”），它是正确的工具。用于一次性绘图使用 [`/plan`](/docs/plan);用于盲目地重新提交相同的提示 N 次使用 `/loop`.

## 开始一个目标

目标模式 由门控 `goal.enabled` 设置，默认情况下处于打开状态。从以下内容开始：

```text
/goal port the importer to streaming and update the call sites
```

omp 将目标固定到会话，注入 `goal` 工具添加到活动工具集中，并在第一回合提交目标。您传递的文本将成为文字 `<objective>` 阻止模型在每个延续中看到的内容，因此将其写成摘要：可交付成果、成功标准、任何不符合捷径资格的内容。

省略参数并 `/goal` 相反，打开目标的多行编辑器。

## 子命令

所有操作都围绕当前会话的目标进行。 `/goal` 如果没有子命令，则针对活动或暂停的目标打开一个交互式菜单。

| 命令 | 效果 |
| --- | --- |
| `/goal set <objective>` | 设定或更换目标。在目标暂停时拒绝；先恢复或放弃它。 |
| `/goal show` | 打印目标、状态、已用Token/预算/剩余Token和已用时间。 |
| `/goal pause` | 停止继续转向。使用量统计冻结；进球记录保留在会话中。 |
| `/goal resume` | 重新启用继续并安排下一次转向。 |
| `/goal drop` | 确认后删除进球记录。累积使用量保留在会话日志中。 |
| `/goal budget <N|off>` | 替换Token预算。 `N` 是Token总数的正整数； `off` 清除上限。 |

`/goal` 当目标已经处于活动状态时，打开管理菜单（`Show details`, `Adjust budget…`, `Pause`, `Drop`）；针对菜单提供的暂停目标 `Resume` 首先。

## 预算限制了循环

如果没有预算，目标模式 就会一直运行，直到模型决定完成为止。这很少是您想要的无人值守会话。盖上盖子 `/goal budget 200000`;该模型还可以通过传递来设置自己的上限 `token_budget` 当它通过创建目标时 `goal` 工具。

预算在其保持活动状态的每个回合中根据目标计算输入、输出和缓存写入标记（缓存读取被排除在外 - 它们是重用的前缀，而不是新的工作）。当使用量超过上限时，状态将变为 `budget-limited` 下一个继续指导被总结提示所取代：告诉模型不要开始新的实质性工作，总结进展，并显示剩余的工作和阻碍。预算耗尽是明确的 **不** 完成 - 指示模型保持目标处于活动状态而不是调用 `complete` 逃离上限。

提高预算 `/goal budget <N>` 然后循环继续。套装 `off` 完全取下盖子。

## 检查和取消

`/goal show` 是读取路径。它打印实时目标、目标状态（`active`, `paused`, `budget-limited`, `complete`, `dropped`）、预算中使用的令牌、剩余令牌以及经过的秒数。

要停止循环：

-   `Esc` 中止当前回合并暂停目标； `/goal resume` 重新启用延续。
-   `/goal pause` 停止继续而不丢失目标或其使用历史记录。
-   `/goal drop` 确认后目标完全结束。

该目标在会话压缩中幸存下来并且 `/branch` / `/fork`。切换工作目录 `/move` 将目标附加到会话，而不是目录。

## 它与普通提示有何不同

在正常会话中，omp 在每个回合后都会停止并等待您。在 目标模式 中，三件事发生了变化，而目标是 `active`:

-   A `<goal_context>` 在每次提示之前都会注入目标和实时预算数字。
-   一个隐藏的 `user` 转向（从可见的记录中被抑制）在每个不调用的回合后排队 `goal({op:"complete"})`.
-   A `goal` 工具被强制进入活动工具集中。该模型使用 `goal({op:"get"})` 阅读自己的预算并 `goal({op:"complete"})` 根据当前回购状态验证每个可交付成果后结束循环。

完成提示有意严格：模型被告知将目标重述为具体的可交付成果，将每个目标映射到文件或命令证据，并在声明完成之前重新读取实际的当前状态。狭隘的支票并不能证明广泛的主张。

## 何时使用哪个

-   **`/goal`** 当目标跨越多个回合时，模型应决定何时完成。验证完成。预算意识。
-   **`/loop`** 当您收到一个提示，要求重新提交固定次数或挂钟窗口时。没有目标，没有完成语义。对于“运行我的测试套件五次并报告碎片”很有用。
-   **`/plan`** 当您希望在进行任何编辑之前对计划角色模型进行只读起草传递时。一回合，然后结构化地移交给执行者。

您可以将它们组合起来：从 `/plan` 确定工作范围，接受计划，然后 `/goal` 反对由此产生的执行长尾简报。
